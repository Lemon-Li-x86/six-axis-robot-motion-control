# 第六阶段交付约束与第五阶段接口冻结（2026-10-29）

本文件对照原项目任务书第 6 阶段“系统测试与项目交付”，用于审查第五阶段新增代码是否会增加后续维护成本。它不是第六阶段已完成的声明。

## 1. 真实任务流程

第六阶段必须在仿真中复现 **原点 → 抓取点 → 中间避障点 → 放置点 → 返回原点**。这个顺序属于应用层任务编排，不属于 APF、IK、PID、FreeRTOS 驱动或 UR5 几何模型。

- **任务描述**：每个场景保存目标位姿、静态障碍物及任务步骤；允许复用一种任务逻辑和多组场景参数。抓取/放置的接触、夹持或虚拟载荷状态必须单独有可检验语义，不能仅用“运动到了抓取点”冒充抓取成功。
- **路径计算**：C APF 接收 base_link 单位 mm 的目标和 AABB，输出纯末端路径。C IK / selector / FK 与梯形段计时继续使用既有生产接口。
- **物理预检**：PyBullet 使用实际加载的 URDF 全连杆离散碰撞检查；C APF **末端点安全间距**与全连杆**最小净距**分别配置。禁止碰撞门禁不通过仍下发命令。
- **执行**：FreeRTOS 轨迹与 Control Task 通过 QEMU UART 发布虚拟驱动目标，PyBullet 反馈真实六关节角。应用层按 ACK 与稳定到位决定是否允许下一段，不得跳过未完成步骤。
- **异常**：任一步骤超时、通信故障、IK 无解、关节越界、碰撞门禁失败必须停止该任务并输出完整的失败原因及未执行段，不得把安全拒绝计为任务成功。

## 2. 参数唯一来源

| 类型 | 目前权威位置 | 不允许的做法 |
|---|---|---|
| UR5 DH/公共坐标变换/关节限位 | `firmware/freertos_demo/model/` 与加载的 URDF（需做一致性验证） | 在 Python 场景里再复制一份“UR5 极限” |
| FreeRTOS 周期、栈、优先级、PID、速度、加速度 | `firmware/freertos_demo/config/robot_defaults.json` 及其生成代码 | 为每条搬运路径再创建一组不一致默认参数 |
| C APF 物理几何及算法行为 | `algorithms/avoidance/potential_field.[ch]` | Python 写另一份相交检测器或算法 |
| 场景专用目标、障碍物和 APF 试验参数 | `simulation/pybullet_ur5/scenarios/` | 把场景位置硬编码进 FreeRTOS Task 或电机驱动 |
| 当前关节反馈、活跃任务、运行故障 | FreeRTOS/虚拟反馈运行状态 | 写入静态模型或全局配置作为“默认状态” |
| 运行时全连杆最小净距/路径采样预算 | 场景验证策略；必须明确标注为**仿真门禁** | 混同于 C APF 末端点 clearance，或静默降低净距以使 CI 通过 |

Python→C IK 的默认 FK 误差限值现在由 `stage5_apf_joint_pose_limits()` 从生产 C 的 `KINEMATICS_IK_MAX_*_RESIDUAL` 唯一来源读取。场景 JSON 不得复制该数值；调用方可主动要求更严，但不能放宽 C 上限。相应 C Host 测试和 PyBullet 测试均应持续覆盖这一接口契约。

## 3. 数据化场景格式

`simulation/pybullet_ur5/scenarios/stage5_static_obstacles.json` 的 `schema_version`、具名场景、末端相对目标、障碍物位置及几何、APF、全臂净距和采样预算，就是第六阶段多场景输入的原型。

后续添加作业步骤/抓取放置事件时应**扩展上层任务格式**，不要修改 C APF 函数签名使其承担搬运业务。旧场景必须继续能被解析，无法识别的 `schema_version` 应拒绝执行，而不是悄悄采用默认值。

## 4. 第六阶段验收所需的证据

严格按任务书四类测试建设自动化：

1. **功能正确性**：多组起点、抓取点、中间障碍和放置点；逐段完成、逆解有效、轨迹误差、实际全连杆净距、回到原点及物体状态。
2. **边界参数**：不可达、奇异、关节限位、零/非法步长、APF 局部极小值、航点和采样预算上限；所有失败必须保持输出原子性。
3. **异常指令**：坏 CRC、丢包、部分 UART 帧、反馈超时、错误命令序列、运行中碰撞与恢复，附日志和故障计数。
4. **连续长时运行**：统计任务成功率、最大与分位轨迹误差、有效物理执行时间、FreeRTOS CPU 占用/抖动、内存和栈水位，并保留可复现配置、ELF/map、协议和 PyBullet CSV。

需要在测试计划中单独声明每个验收阈值，不能把“绿灯”当成所有指标合格。QEMU 性能与真实 Cortex-M4 硬件耗时不能混用。

## 4.1 Stage5 剩余门禁不得在 Stage6 中被假定完成

若按照原 PDF 严格考核，第五阶段仍有固件端 APF 编排、性能优化证据与 legacy GUI 收敛三个明确保留项，见 [项目大纲逐项进度审计](../project_plan_progress_audit_2026-10-31.md)。Stage6 允许围绕**已验证的受控软件执行接口**准备任务状态机，但新应用不得引用不存在的“固件自主 APF 功能”，也不得在未补验前把 Stage5 标为全项通过。

## 5. 提交与交付流程

先以可单独撤销的分支合并小型 C 算法/几何接口；然后验证 PyBullet 物理门禁；最后才接 UART/FreeRTOS。每次合并依赖本次提交的 GitHub Actions 实际结果。第六阶段交付包应包含固件源码、运行配置、仿真场景、独立测试记录、开发/使用说明、问题追踪、实验视频和最终项目总结。

**截至 2026-10-31 的更新**：Stage5 静态被阻挡场景 C APF/IK → QEMU FreeRTOS UART → PyBullet 实际逐段执行已通过 4/4 压缩与 28/28 未压缩路径，Windows 原生 GUI SAFE JOG + C 回位也通过，见 [Stage5 最终有保留签收](../part5/17_stage5_final_acceptance_2026-10-31.md)。未解决的 `six_axis` legacy Linux 原生 GUI 收敛见 [Issue #34](https://github.com/Lemon-Li-x86/six-axis-robot-motion-control/issues/34)；不能把 Stage5 PR #33 的 Draft 状态当成已合并。**第六阶段的虚拟抓取/放置、完整搬运、多场景和长时运行尚未开发验收**。上层编排应复用已验证的受控 C/UART 物理闭环，不以历史 GUI 鼠标点动为依赖。
