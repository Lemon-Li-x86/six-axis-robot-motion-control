
# 项目开发与文件管理规范

## 1. 构建管理

CMake 是嵌入式固件和 QEMU 测试的唯一正式构建系统。

- 不再手写第二套 GCC 源文件编译清单。
- 新增 .c 文件时，显式登记到对应 CMake 目标。
- 构建产物统一放入 build/。
- 自动生成的头文件不得手工修改。
- 正式固件与独立测试目标分别管理。

## 2. 新功能开发流程

每个新功能按以下顺序开发：

1. 确定功能所属模块。
2. 确定公开 API。
3. 明确输入、输出、数据单位和错误码。
4. 确定边界条件与测试方法。
5. 实现最小可用功能。
6. 添加测试。
7. 编译、运行并验证。
8. 更新必要的文档。

## 3. 文件命名

采用能够表达职责的文件名。

例如：

motion_limits.c
motion_solution_selector.c
trajectory_generator.c
pid_controller.c

避免使用：

motion_new.c
motion_final.c
motion_v2.c
test_latest.py

历史版本通过 Git 保存。

## 4. 文件拆分规则

以下情况考虑拆分文件：

- 一个文件承担多种不相关职责。
- 模块难以独立测试。
- 上下层依赖混乱。
- 修改一个功能经常影响无关功能。
- 多处出现重复实现。

不以单纯的代码行数作为拆分依据。

## 5. 测试管理

测试应与功能同步开发。

- 算法尽可能独立于操作系统进行测试。
- QEMU 测试使用独立入口。
- 正式固件不应长期强制包含开发自测。
- 编译成功不等于测试通过。
- 测试报告应记录条件、结果和判定标准。

临时结果存入 build/。

需要长期保存的测试结果放入 docs/testing/，
并记录对应代码版本和测试环境。

## 6. Git 管理

提交前执行：

git status --short
git diff --check
git diff --stat

提交应尽量做到一个主题对应一个 commit。

推荐前缀：

feat: 新功能
fix: 缺陷修复
refactor: 行为不变的重构
test: 测试变更
build: 构建系统变更
docs: 文档变更

原则上不要将大规模重构和新算法实现混为一次提交。

## 7. 架构扩展

轨迹规划、控制算法和新增硬件平台应在真正开始开发时引入对应模块。

已经稳定的模块通过明确的公开接口与新增模块交互。

禁止为了新增功能而随意修改不相关模块。

所有结构调整必须保留可验证的构建与测试结果。
